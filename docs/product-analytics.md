# Athlete product analytics

B2C only. The operational dashboard is unchanged; `/admin/analytics` links back to it. Individual profiles have a paginated Activity section. Reports and individual timelines require the existing effective-admin dependency, including email allowlisting; SQL projections and RPCs are service-role only. Ordinary athletes cannot query other athletes or choose the actor/timestamp of an event.

## Architecture audit and evidence

| Source | Use | Historical limitations |
| --- | --- | --- |
| profiles | Signup, professional status, combat sports, starting path | No invented acquisition attribution. Explicit `analytics_excluded` flag for internal/test athletes; role admins and configured admin email allowlist excluded automatically. |
| plans | Generated plans, earliest ready/publishable plan | Generation is not engagement; original creation time is the existing first-usable-plan proxy, not a historical ready-state transition. |
| session_completions | Observed starts, done/modified completions, plan usage | Only explicit started_at/completed_at; no inferred starts for completions lacking one. |
| external_training_sessions | Saved manual sessions | Excludes deleted records. A saved manual log is a completed action; not an observed session start. |
| sparring_logs | Saved logs | Linked manual sessions can appear under both manual and sparring features; athlete/day counts deduplicate across features. |
| today_checkins, daily_checkins | Completed recovery check-ins | Original creation times; no clinical values selected. |
| session_logs | Legacy completed training logs/history | Kept as historical logged actions; no longer an active write route. |
| custom_training_plans | Athlete-created plans | Creation is meaningful; generated plans are not. |
| beta_feedback | Submitted session feedback | Only identity and original timestamp; no comments, screenshots or health context selected. |
| generation_jobs | Failed generation requests | Creation date groups failed jobs; no invented terminal failure time or downstream causal claim. Existing control-room diagnostics retain technical details. |

A private SQL view unions existing records, without copying them. One service-only RPC aggregates actions by athlete, UTC day, feature and action before transfer; Python computes cohort/set metrics from those reduced facts. It returns a JSON envelope so PostgREST's default row cap cannot silently truncate metrics. The report fetches complete reduced history to support accurate first action and cohort denominators. For very large populations this can still require a future SQL-only report RPC/materialized daily aggregates; no speculative pipeline or cache is introduced now. The athlete timeline is paginated at the database. New event and source athlete/day indexes support the reads.

## Missing interactions

`product_events` records only controlled event names, a controlled feature, authenticated athlete ID, server time, retry ID and optional UUID flow identity. There are no free-text payloads, URLs, device IDs, health details, notes, nutrition contents or third-party analytics. Browser discovery/edit/nutrition-save counters deduplicate by athlete, feature, resource and UTC day. Thus nutrition is **save-days**, not a fabricated count of food entries; repeat saves/refreshes do not inflate adoption. Free-round timer transitions use stable hashed run/round identities; resumed/retried transitions deduplicate. Closed browsers/offline interactions are not queued or replayed with invented timestamps. Explicit timer exits are observed exits; a missing completion alone is not an exit.

Plan views, custom-plan editor opens/edits, replacements, history opens, nutrition opens/saves, feedback prompt impressions and free timer starts/rounds/completions/exits are optional events. Frontend exception counts come from Sentry's existing `beforeSend` callback; technical error content stays in Sentry. API friction counts only authenticated failed feature writes (selected 400/409/422/5xx responses), using existing middleware identity and request IDs, without logging request bodies or exception text again. Events never affect the primary operation's outcome. No Sentry replacement or analytics dependency is installed.

Onboarding start/completion use dedicated, server-owned workflow timestamps, recorded by the existing authenticated profile/draft write routes. A draft save records a start. Saving a starting-path choice after existing compliance validation records completion (and start if none exists). Repeated saves preserve the original times. Both plan-first and tracking-first complete this workflow without requiring generation. There is no backfill of these new timestamps. Showing the starting-path page alone does not establish an attempted onboarding action.

## Exact definitions

- Active: at least one recorded meaningful action (training start/completion, manual training save, check-in, sparring log, custom plan creation/edit, session feedback, timer start/round/completion, nutrition save-day). Sign-in, page/feature opens, generated plans and profile updates are excluded.
- DAU/WAU/MAU: distinct active athletes over today and preceding 0/6/29 UTC calendar days, anchored to report time regardless of selected report period. Stickiness = DAU / MAU.
- Period: today and preceding N−1 UTC calendar days (7/30/90), or complete available history. Previous period is the immediately preceding equal-length calendar interval. All time has no comparison. Segment selection applies to both intervals.
- Registered: all eligible athletes after segment filters, regardless of report period. Ever-active: those with any recorded meaningful action. Average active days = meaningful athlete-days in selected period / all eligible registered athletes, including inactive athletes.
- Conversion: numerator and denominator shown on every card. Signup conversions use signups in the report period. Plan conversion includes only onboarded athletes choosing plan-first; tracking-first users are not failures. First-to-second-active-day conversion excludes first actions today. Time to first action is median signup-to-first-recorded-action duration among activated signup-cohort athletes.
- Dn retention: signup-date+n UTC day contains a meaningful action. Only signup cohorts whose entire Dn day has elapsed enter that denominator; today’s incomplete return day is excluded. D1/D7/D30 are exact-day returns, not rolling ranges. Weekly cohorts group signup dates by UTC Monday and retain the same per-athlete maturity rule.
- New active: first recorded action falls within period; returning active: first recorded action precedes period. This is first **recorded** use, not proof of first lifetime use.
- Inactive 7/14/30: previously active athletes whose last recorded action is at least that many elapsed days ago. Never-active athletes are separate. Profile inactivity duration displays calendar days.
- Feature adoption: distinct meaningful feature users / eligible registered athletes. Actions, repeat users (2+ meaningful UTC days), and discovery users are separate. Plan/custom creation, training starts and rounds can occur in a single session; they count as actions, but do not inflate repeat-day users. History adoption attributes existing strength/manual completions to session logging without duplicating stored rows or timeline events. Feedback completion compares unique prompted athletes with those subsequently submitting feedback in the period, not a per-prompt response rate. Matched strength/timer start-to-completion rates use persisted session/run identities. Generated-plan subsequent use requires a matching completed/modified planned session.
- Unresolved session start: observed persisted start older than 24h with no done/modified completion. Not proof of intent. Onboarding unresolved stages use observed timestamps older than 24h. Repeated discovery requires 2+ observed opens with no meaningful action; absence of historical tracking is unknown.
- Error follow-up: affected athletes with a fully elapsed seven-day window after last observed feature/category error; reports whether meaningful activity was recorded in that window. Does not imply causation or prove abandonment. Failed generation jobs lack exact error timestamps for this calculation and are omitted.

Feature-only interactions and onboarding timing have no pre-release history. Consent refusal and 180-day expiry undercount optional features. First/last activity always mean first/last available verified record. No historical zero should be interpreted as proof that someone did not use an uninstrumented feature. Acquisition source is unavailable; missing sport/status is unknown. Plan-free segmentation means no recorded usable plan, not an inferred preference. Segments use current saved profile attributes, not reconstructed historical values.

## Migration, security and privacy review

Apply `20261025112935_athlete_product_analytics.sql` before deploying application code. No business rows are duplicated or historical action timestamps invented. It adds a minimal interaction table, consent preference, exclusion flag and onboarding timestamps; private views/RPCs enforce existing service boundaries. Retry uniqueness, daily discovery/save deduplication and a serialized 120-events/minute/athlete and 1,000-events/day/athlete caps limit collection. Account deletion cascades events/preferences. All event inserts are server-owned; the browser cannot directly call the database ingestion function.

UK GDPR/PECR review: existing first-party saved service records are reused under the existing service-improvement/fault-investigation purposes; administrators must maintain the service-improvement legitimate-interest assessment and honour objections using `analytics_excluded`. Optional behavioural measurement requires a separate, freely refusable, default-off account choice. It is not bundled with Terms or health consent and never blocks a feature. The choice is in Settings → Privacy and a collapsed option after starting-path choices. No additional cookie/localStorage identifier, replay, fingerprint or third-party recipient is introduced. Optional tracking is disabled for minors server-side, pending any age-appropriate consent/DPIA work. Sentry remains the existing processor; only categorical counts stay in Supabase. This technical review does not replace the controller’s records of processing, lawful-basis assessment, DPIA or published notice review.

Events expire after 180 days. Migration schedules `prune_product_events()` daily through existing pg_cron when installed. If pg_cron is absent, deployment **must** arrange that same function through an existing maintenance schedule before enabling optional tracking; no new scheduler is installed automatically. Check `cron.job` and job health. Onboarding workflow timestamps follow profile retention, and existing service records retain their existing deletion policies. Disabling optional analytics stops event ingestion immediately at the database; it does not erase existing service records. Event retention is independent of consent withdrawal; deletion requests use the existing account/privacy process.

To exclude an internal/test athlete, use an authorised service/admin database session: `update public.profiles set analytics_excluded=true where id='<verified athlete UUID>';`. Do not infer internal status from arbitrary email patterns. Do not grant clients write access to the exclusion flag or onboarding timestamps.
